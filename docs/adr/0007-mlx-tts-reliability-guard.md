# MLX TTS 可靠性守护：防病态生成、快速失败、僵死自愈

小智侧对 MLX TTS 服务（单线程 HTTPServer，见 ADR-0004）加三层守护，MLX 服务本身零改动：孤立拟声词不送合成、逐句条目 20s 短超时、请求超时后健康探测并 kickstart 自动拉起（5 分钟节流）。

## Context（取证）

- 2026-08-28 03:37 事故：真机"哎，你在吗？"无回复。日志取证（`~/.hermes/logs/mlx-tts-server.log`）：
  - `TTS: "嗯..." → 327.7s 音频, 生成 181.5s` —— **单字拟声词诱发 Qwen3-TTS 病态长生成**（复读机式拖长），推理占死单线程 3 分钟；
  - 随后下一个请求推理**挂死不返回**，服务进程活着但 `/health` 无响应（僵死），launchd KeepAlive 只处理进程退出、不处理僵死；
  - 客户端 60s 超时断开 → 服务端算完写响应 `BrokenPipe`（历史 23 次）；重启后重试请求又撞上 ~157s 模型加载期再次超时，形成连环失败。
- 用户曾怀疑并发问题：**并行度无关**。该服务是 `HTTPServer` 单线程同步实现，天然串行（并行度恒为 1），无可设并发参数。

## Consequences

- `base.to_tts_stream` 过滤孤立拟声词（嗯/啊/哦等单字，含带标点形态）：它们无合成价值且是病态生成诱因；"嗯嗯""好呀"等多字短语仍正常合成（保守策略，病态谱未完全摸清）。
- MLX 三个逐句流式条目 `tts_timeout: 20`（正常句 3~8s）：异常 20s 内暴露，触发守护；整段 `MlxTTS` 维持 60s。
- `mlx.py` 请求超时/连接失败后探测 `/health`（2s）：无响应即 `launchctl kickstart com.yuanbao.mlxtts`，节流 5 分钟防重启风暴。kickstart 后模型重载约 2~3 分钟，期间请求仍会失败——由既有重试兜底，不做加载等待（避免阻塞 TTS 线程）。
- 病态生成谱（哪些文本会诱发）未完全摸清，若再现长推理占死，下一步考虑在 MLX 侧加推理长度上限（需跨生态改动，暂不做）。
