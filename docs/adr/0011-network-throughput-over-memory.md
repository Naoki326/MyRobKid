# 网络吞吐取向：从省内存回到吞吐

> **状态：部分回退（2026-09-12）。** 本文的 Context 与取证有效，但**Decision 的前提
> 已被推翻**：首版实施后设备 OOM（free sram 41067 → 9919，`Failed to create
> music start task`），接收缓冲与 lwIP 窗口已回退，只保留 IRAM 加速。
> **关键修正：这块板的内部 SRAM 已被 camera/LVGL/AFE 吃紧，那套「省内存配置」
> 是为省内存选的，不是上游错配——本改动的本质是「用有限内存换吞吐」，不是
> 「纠正错配」。** 详见「内存账」与「实施进度」。目标吞吐需重定，只改 sdkconfig
> 达不到。

机器人固件的 WiFi/网络栈配置从上游继承了一套**省内存优先**的取向（关掉 WiFi 驱动 IRAM 加速、接收缓冲与聚合窗口取最小值、lwIP 接收窗口取最小值）。本文**初版**据此判定：该取向在 ESP32-S3 上作废，按吞吐取向重置配置。

**但该判定建立在一个未经验证的前提上——「这台设备的内存有余量可供挥霍」。2026-09-12 的实测推翻了它。** 修正后的结论是：这套配置是**在有限内存下做的正确取舍**，吞吐问题的出路不是「把参数调大」，而是**让网络缓冲搬到 PSRAM**、以及**解开上游组件里的调度天花板**（接收任务优先级、读粒度、反压上限）。详见「内存账」一节。

## Context

### 症状与取证

OTA 与内容下载时，屏幕上的进度数字封顶在 20KB/s 上下；音乐播放期间下载吞吐恰好等于消耗速度（实测 `8KB/s`，而 64kbps 的流正好消耗 `8KB/s`），没有余量，任何波动就是卡顿。ADR-0008 已把后者追到「AFE 占满 CPU0、接收任务优先级低」，但那只是**同一条吞吐瓶颈在音乐场景下的表现**，不是全部。

「屏幕上的 20KB/s 是 WiFi 上限」是本次误判的起点。三份独立证据否定它：

| 证据源 | 观测 | 含义 |
|---|---|---|
| 串口 OTA 采样（09:03 一次） | 峰值 **63.2KB/s**，区间平均 **31.6KB/s** | 同一天同一台设备，是 20KB/s 的 3 倍 |
| 串口 OTA 采样（11:0x 一次） | 峰值 **20.3KB/s**，区间平均 **10.9KB/s** | 抖动跨 3 倍，**单次瞬时值不可作基线** |
| nginx access 日志 | 同一次 3,491,280 字节下载的 `request_time` 出现过 53s / 151s / 237s / 284s（≈64 / 23 / 14 / 12KB/s）| 与串口采样同量级——瓶颈不在服务端 |

旁证：Mac 侧从同一地址 `curl` 同一个固件包是 **277MB/s**，nginx 未设 `limit_rate`；设备上报 RSSI 为 **-41 ~ -54 dBm**（信号很好，不是弱信号降速）。

**关键纠正：屏幕上的 KB/s 不是链路速率，它是应用层每秒读到的字节数**，串了 flash 顺序写、日志打印与调度停顿。用它当「WiFi 上限」的探针，量到的其实是固件自己。这也是本 ADR 要自测入口、而不要屏幕数字的原因。

### 病因：三处省内存取向的错配

1. **WiFi 驱动 IRAM 加速被显式关闭**（`CONFIG_ESP_WIFI_IRAM_OPT=n`、`CONFIG_ESP_WIFI_RX_IRAM_OPT=n`）。IDF 官方帮助原文即为「省下 10KB / 17KB IRAM，但 WiFi 吞吐/性能下降」，两者默认都是 `y`。本项目从上游（ESP-HI / ESP32-C3）复制而来。
2. **接收缓冲与聚合窗口取最小值**：静态接收缓冲 3（IDF 默认 10）、动态接收缓冲 6（默认 32）、接收块聚合窗口 3（默认 6）。IDF 帮助明说静态缓冲数**建议 ≥ 聚合窗口**——当前配置把这条关系也压没了。
3. **lwIP 接收窗口取最小值**：`CONFIG_LWIP_TCP_WND_DEFAULT=5760`（= 4×MSS，IDF 默认值），IDF 帮助原文为「更小的接收窗口省一点 RAM，但会**显著**降低性能」。

叠加两处**上游网络组件内部写死**的天花板（本仓不可改，见 Consequences）：网络数据唯一搬运任务的优先级为 **1（全系统最低）**；HTTP 客户端接收反压上限 **8KB**。ADR-0008 已实测过前者在音乐场景的后果（吞吐掉到 7KB/s）。

### 内存账（**本节初版结论是错的，已重写**）

初版本节只看**静态段占用**就下了「余量安全」的结论——这是本次失误的直接来源。
**静态段有余量 ≠ 运行时堆有余量**，而后者才是设备真正会 OOM 的那个。

链接结果实测（ESP32-S3，IRAM/DRAM 共享 333.8KB 段，`iram0_0_seg`）：

| 项 | 初版（改动前） | 首版改动后（2.4.24） |
|---|---|---|
| 指令文本 `.iram0.text` | 86,016（84.0KB，25.2%） | 100.5KB（30.1%） |
| 数据 + BSS | 76,016（74.2KB，22.2%） | 74.2KB（不变） |
| 静态剩余段 | 179,728（175.5KB） | 159.0KB（47.7%） |

静态看确实「安全」。**但设备实测的运行时常驻内部 RAM 是另一回事：**

| | free sram | minimal sram |
|---|---|---|
| 改动前（2.4.20/2.4.23） | 41,067 | 33,275 |
| 首版改动后（2.4.24） | **9,919** | **2,095** |

并伴随 `E Application: Failed to create music start task`（OOM 的直接症状）。

**30.4KB 的损失拆解**（已核到项）：

| 项 | 代价 | 性质 |
|---|---|---|
| `IRAM_OPT` / `RX_IRAM_OPT` | **17.8KB** | `_data_start` 从 `0x3fc9d000` 上移到 `0x3fca1700`——**IRAM 文本与 DRAM 数据共享同一段**，文本变长就把数据段往后推，堆被真实吃掉 |
| 接收缓冲 3→8 / 6→16 / BA 3→6 | ~8KB+ | 静态/动态 RX 缓冲每块约 1.6KB |
| lwIP 窗口 5760→16384 ×2 | 20.8KB/socket | TCP_WND 与 TCP_SND_BUF 是**真实分配**，不是窗口通告名义值 |

**两条错误的本质**：

1. **把 lwIP 窗口当成不花内存的旋钮。** 它是真金白银，且带宽时延积（BDP）
   分析表明它**从来不是瓶颈**：局域网 RTT 3.5–30ms 下 5760B 窗口的理论上限是
   188–1607KB/s，而验收目标才 200KB/s。原值 5760 从未限制吞吐，提它纯属浪费。
2. **以为 IRAM 加速是「段内挪移、不占运行时堆」。** 链接脚本直接推翻了这一点
   （`_data_start` 确实上移）。它是吞吐的唯一真实来源，但代价也是真实的。

**修正后的结论：这次改动的本质是「用有限的内存换吞吐」，而不是「纠正一个
上游错配」。** 首版把它当作后者，方向就错了。这块板的内部 SRAM 已被
camera/LVGL/AFE 吃紧——原值 3/6/3 + 5760 是为省内存**选的**，不是错配。

**真正的出路是让网络缓冲走 PSRAM**（`SPIRAM_TRY_ALLOCATE_WIFI_LWIP`）：
把缓冲从内部 SRAM 搬到 8MB PSRAM，才能同时要吞吐与内存。它的代价是 IDF
警告的额外延迟（与 ADR-0003 的音频延迟域冲突），**必须单独验证延迟后再上**，
不能与配置层混做。

## Decision

### 1. 配置层（**初版数值已回退；现只保留 IRAM 加速**）

**初版决定（已作废，保留供追溯）**：恢复 IRAM 加速 + 把接收缓冲提到 8/16/6 + 把 lwIP 窗口提到 16384。**这组值已回退**——它们共吃 30.4KB 运行时常驻内存，把设备打到 OOM。

**现行决定（回退后）**：

- 恢复 WiFi 驱动 IRAM 加速（两项）。代价 **17.8KB** 运行时常驻内存（`_data_start` 上移），
  但它是 IDF 文档明确认可的吞吐手段（关掉会降吞吐），也是本次唯一保留的一项。
- 接收缓冲与聚合窗口**维持原值** 3/6/3。原值是为省内存**选的**，不是错配。
- lwIP 的 TCP 接收窗口与发送缓冲**维持原值 5760**，并**显式写出**（不靠缺省）。
  理由不是「省内存」而是「没必要」：BDP 分析表明局域网下 5760B 窗口的理论上限
  是 188–1607KB/s，而验收目标才 200KB/s——**它从未限制过吞吐**。
- **不启用** `SPIRAM_TRY_ALLOCATE_WIFI_LWIP`：初版的理由是「延迟」。
  **回退后这条理由已不成立——它现在是吞吐的**唯一出路**。** 它把网络缓冲从
  内部 SRAM 搬到 8MB PSRAM，才能同时要吞吐与内存；代价是 IDF 警告的额外延迟
  （与 ADR-0003 的音频延迟域冲突，因为音频同走 TCP）。因此它必须**单独验证
  延迟**后再上，不能与配置层混做。这是下一个要做的实验，也是本 ADR 当前
  最高优先级的待办。
- **不启用** TCP 窗口缩放（`LWIP_WND_SCALE`）：它影响**所有**连接，包括 60ms/帧的音频 WebSocket；收益在大文件、风险在音频，不属本次范围。

### 2. 组件层（收编上游网络组件后修改，独立一次 OTA）

上游网络组件（`78/esp-ml307`）内部创建网络数据唯一的搬运任务，并写死三处限制，必须把该组件从 `managed_components/` 收编进主仓才能改：

- 接收任务优先级 1 → **≥3**，并与 WiFi/TCPIP 任务所在核协调（WiFi 任务固定 CPU0，音频输入/AFE 也压 CPU0）。
- 接收缓冲每次 1500 字节 → **4096 字节**，降低每字节的系统调用与上下文切换开销。
- HTTP 客户端接收反压上限 8KB → **32KB**（按实测内存调整）。语义须写清：这是**反压上限，不是速率上限**——它决定接收任务能有多大的提前量去填缓冲，不决定速率。

**收编的理由与代价**：`managed_components/` 已入库忽略、由依赖锁重建，**写在那里的任何改动都会在下次依赖解析时消失**，故不能就地改。收编后上游更新不再自动流入，这是本决策的主要代价，须在组件目录留下「本仓改了哪几处」的说明。

### 3. 基线层（自测入口 + 配置契约）

- **设备端吞吐自测入口**（作为一个 `self.` 设备工具）：报告均值 / 中位数 / 最小值 / 字节数 / 耗时 / 信号强度 / 信道 / 当前省电档。选它而非「读 OTA 每秒日志」，因为后者只有升级时才有数字且抖动跨 3 倍（见证据表）。
- **配置契约断言**（纯逻辑，随提交运行）：解析 `sdkconfig.defaults` 与 `sdkconfig.defaults.esp32s3`，断言吞吐相关选项不低于目标值。**这条不可省**——配置被改回低值后设备仍能正常启动，运行时行为覆盖不到这种回退。
- **验收阈值**：自测均值 ≥ **200KB/s**、最小值 ≥ **100KB/s**；内容/音乐路径 ≥ **32KB/s**（4× 于 64kbps 消耗）。名义目标，实施时按实测校准。
- **不倒退约束**：待机省电档不变、对话期全速档不变（ADR-0003）、内部 RAM 运行余量不跌破历史断连水位（free sram 曾跌破 17KB 导致 WiFi 断连）。
- **一次只改一组**：配置层与组件层分两次 OTA 各测一次。ADR-0008/0009 的共同教训是「多项混改会丧失归因能力，逐项排除走了 6 版」。

## Consequences

- **屏幕上的瞬时速度不再被当作链路指标**：OTA 进度显示改为「滑动中位数 + 累计平均」，瞬时值只进串口（串口是取证源，屏幕是体验面）。这条纪律比数字本身更重要——本次误判正是从误信屏幕数字开始的。
- **两处上限的修改点在本仓之外**：不改上游组件，配置层做得再对也够不到 200KB/s，因为搬运任务优先级为 1、接收缓冲 1500 字节、反压 8KB 三处写死在组件里。这是「配置改不动吞吐」这个直觉的例外，须在实施时先做配置层再收编组件，否则无法归因。
- **收编产生长期维护成本**：组件更新需手工比对，且与 ADR-0002 已登记的同类问题（`78__esp-wifi-connect`、`txp666__otto-emoji-gif-component` 也是不入库的本地修改组件）叠加——本项目已有 **3 个**本地修改的组件靠「构建前复制」或「收编」维持，这条路径上没有上游自动同步。下次再有第四个时，应当先问是否该整体转 fork 工作流。
- **内存余量成为回归观测项**：恢复 IRAM 加速吃 27KB 剩余堆，放大接收缓冲再吃内部 RAM。改动后须复核段占用与运行余量；余量跌破安全间隔时，优先回收的是缓冲放大项（它是收益递减的一端），不是 IRAM 加速（它是吞吐的主要来源）。
- **待机功耗不受影响**：本决策只动驱动/协议栈参数，不动省电档的设定点与让位机制（ADR-0009 的范围）。
- **不是 bug 的假问题，勿修**：`CONFIG_ESPTOOLPY_FLASHMODE` 的字符串值是 `dio` 而 QIO 选项开启，这是 IDF 的正常设计（bootloader 先以 DIO 烧写、启动后自行升级到 Quad 模式）。
- **若仍不达标，排查方向在设备之外**：2.4GHz 信道拥塞与同频干扰、AP 的省电/聚合设置、距离遮挡、其它高流量设备。这些属另一张票，本 ADR 不为它们留口子。

## 实施进度

- **2026-09-12：首版配置层导致设备 OOM，已部分回退。** 教训写在「内存账」一节。
  当前状态：接收缓冲与 lwIP 窗口已回退到原值（**并显式写出** 3/6/3 + 5760），
  **只保留 IRAM 加速**（代价 17.8KB 堆）。预期设备回到 40 − 17.8 ≈ 22KB 水位，
  **待上机实测确认**；若仍偏低则连 IRAM 加速一起回退，那等于本改动收益归零，
  需重评整条路径。回退提交 `d02cada`。
- **契约测试方向已纠**：首版锁的是「不低于 IDF 默认」的**下限**——恰好会放行
  本次的 OOM 改动。现改为锁**上限**（这组值不得高于当前值）。
- **取证口径**：`sdkconfig` 由 `scripts/build.py zhengchen/minicam --name zhengchen-minicam`
  重新生成（不要裸跑 `idf.py reconfigure`，详见 ADR-0002 的四路径实测表）。
  本次顺带修正一组**预存漂移**：`CONFIG_EMOTE_DEF_BG_COLOR/FONT_COLOR`
  入库值是黑底白字，重新生成后回到板卡预设的米色底黑字
  （`0xC2B280/0x000000`）——该漂移先于本 ADR 存在，需在设备上确认屏幕配色。
- **待办（顺序不可颠倒）**：
  1. 上机实测回退后的 free sram，确认 22KB 水位安全；
  2. **重写本 ADR 的目标**：200KB/s 是未考虑内存约束时定的，而只改 sdkconfig
     达不到——需要「网络缓冲 PSRAM 化」这条独立路径，先验延迟；
  3. 组件层（收编上游网络组件改接收任务优先级/缓冲/反压）未动；
  4. 基线层（吞吐自测入口 + 屏幕改中位数/均值）未动。

## 附：术语

新增**网络吞吐基线**：设备端吞吐自测入口 + 入库的目标数值契约 + 本条 ADR 的验收阈值三者合称；与**管线遥测**（音乐播放链路的 `pipe:` 行）是两套指标，前者测链路、后者测播放链路，勿混。
