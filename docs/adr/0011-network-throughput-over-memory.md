# 网络吞吐取向：从省内存回到吞吐

机器人固件的 WiFi/网络栈配置从上游继承了一套**省内存优先**的取向（关掉 WiFi 驱动 IRAM 加速、接收缓冲与聚合窗口取最小值、lwIP 接收窗口取最小值），这批配置足以让设备在 ESP32-S3 上正常跑起来，但把网络吞吐压在远低于芯片能力的量级。决定：**该取向在 ESP32-S3 上作废**，按吞吐取向重置配置，并把「目标吞吐」写成入库的配置契约、把「实测吞吐」做成设备端可随时叫起的自测入口（issue #23）。

## Context

### 症状与取证

OTA 与内容下载时，屏幕上的进度数字封顶在 20KB/s 上下；音乐播放期间下载吞吐恰好等于消耗速度（实测 `8KB/s`，而 64kbps 的流正好消耗 `8KB/s`），没有余量，任何波动就是卡顿。ADR-0008 已把后者追到「AFE 占满 CPU0、接收任务优先级低」，但那只是**同一条吞吐瓶颈在音乐场景下的表现**，不是全部。

「屏幕上的 20KB/s 是 WiFi 上限」是本次误判的起点。三份独立证据否定它：

| 证据源 | 观测 | 含义 |
|---|---|---|
| 串口 OTA 采样（09:03 一次） | 峰值 **63.2KB/s**，区间平均 **31.6KB/s** | 同一天同一台设备，是 20KB/s 的 3 倍 |
| 串口 OTA 采样（11:0x 一次） | 峰值 **20.3KB/s**，区间平均 **10.9KB/s** | 抖动跨 3 倍，**单次瞬时值不可作基线** |
| nginx access 日志 | 同一次 3,491,280 字节下载的 `request_time` 出现过 53s / 151s / 237s / 284s（≈64 / 23 / 14 / 12KB/s）| 与串口采样同量级——瓶颈不在服务端 |

旁证：Mac 侧从同一地址 `curl` 同一个固件包是 **277MB/s**，nginx 未设 `limit_rate`；设备上报 RSSI 为 **-41 ~ -54 dBm**（信号很好，不是弱信号降速）。

**关键纠正：屏幕上的 KB/s 不是链路速率，它是应用层每秒读到的字节数**，串了 flash 顺序写、日志打印与调度停顿。用它当「WiFi 上限」的探针，量到的其实是固件自己。这也是本 ADR 要自测入口、而不要屏幕数字的原因。

### 病因：三处省内存取向的错配

1. **WiFi 驱动 IRAM 加速被显式关闭**（`CONFIG_ESP_WIFI_IRAM_OPT=n`、`CONFIG_ESP_WIFI_RX_IRAM_OPT=n`）。IDF 官方帮助原文即为「省下 10KB / 17KB IRAM，但 WiFi 吞吐/性能下降」，两者默认都是 `y`。本项目从上游（ESP-HI / ESP32-C3）复制而来。
2. **接收缓冲与聚合窗口取最小值**：静态接收缓冲 3（IDF 默认 10）、动态接收缓冲 6（默认 32）、接收块聚合窗口 3（默认 6）。IDF 帮助明说静态缓冲数**建议 ≥ 聚合窗口**——当前配置把这条关系也压没了。
3. **lwIP 接收窗口取最小值**：`CONFIG_LWIP_TCP_WND_DEFAULT=5760`（= 4×MSS，IDF 默认值），IDF 帮助原文为「更小的接收窗口省一点 RAM，但会**显著**降低性能」。

叠加两处**上游网络组件内部写死**的天花板（本仓不可改，见 Consequences）：网络数据唯一搬运任务的优先级为 **1（全系统最低）**；HTTP 客户端接收反压上限 **8KB**。ADR-0008 已实测过前者在音乐场景的后果（吞吐掉到 7KB/s）。

### 内存账（为什么「省内存」是可以放弃的）

链接结果实测（ESP32-S3，IRAM/DRAM 共享 333.8KB 段）：

| 项 | 字节 | 占比 |
|---|---|---|
| IRAM 段总长（`iram0_0_seg`） | 341,760（333.8KB） | 100% |
| 指令文本 `.iram0.text` | 86,016（84.0KB） | 25.2% |
| 数据 + BSS（`.dram0.data` + `.dram0.bss`） | 76,016（74.2KB） | 22.2% |
| **剩余堆** | **179,728（175.5KB）** | **52.6%** |

恢复两项 IRAM 加速约需 **27KB**，占剩余堆的 15%。运行时空闲内部 RAM 约 36–42KB、保留区 96KB——**余量够，但改动后必须复核段占用**（内存账是 Decision，不是 Assumption）。

**改动后实测（2.4.24 首版配置层，已复核）**：指令文本 84.0 → **100.5KB**（+16.5KB，即 IRAM 加速的代价），数据 + BSS 74.2KB 不变，剩余堆 175.5 → **159.0KB**（47.7%）。消耗比预估的 27KB 少一半（IDF 只把「频繁调用的」那部分搬进 IRAM），余量安全。

## Decision

### 1. 配置层（纯数值，风险最低，与第二层分两次 OTA）

- 恢复 WiFi 驱动 IRAM 加速（两项）。
- 接收缓冲与聚合窗口向 IDF 默认靠拢但**不照抄**（保留内存余量）：静态 3 → **8**、动态 6 → **16**、接收聚合窗口 3 → **6**。
- 提高 lwIP 的 TCP 接收窗口与发送缓冲默认值（5760 → 目标值），未开窗口缩放时上限 65535。
- **不启用** `SPIRAM_TRY_ALLOCATE_WIFI_LWIP`：它省内部 RAM，但 IDF 警告会引入额外延迟，与本项目音频路径对延迟的敏感（ADR-0003 的省电锯齿同源）冲突。代价是放弃 IDF 在 PSRAM 模式下为这两个缓冲给出的更高默认值（16/16），以及 IDF 对「聚合窗口 ≥16 才能与 AP/STA 更好兼容」的建议——本网络实测信号 -41~-54dBm、无兼容性症状，暂不采纳。
- **不启用** TCP 窗口缩放（`LWIP_WND_SCALE`）：它影响**所有**连接，包括 60ms/帧的音频 WebSocket；收益在大文件、风险在音频，不属本次范围。

### 2. 组件层（收编上游网络组件后修改，独立一次 OTA）

上游网络组件（`78/esp-ml307`）内部创建网络数据唯一的搬运任务，并写死三处限制，必须把该组件从 `managed_components/` 收编进主仓才能改：

- 接收任务优先级 1 → **≥3**，并与 WiFi/TCPIP 任务所在核协调（WiFi 任务固定 CPU0，音频输入/AFE 也压 CPU0）。
- 接收缓冲每次 1500 字节 → **4096 字节**，降低每字节的系统调用与上下文切换开销。
- HTTP 客户端接收反压上限 8KB → **32KB**（按实测内存调整）。语义须写清：这是**反压上限，不是速率上限**——它决定接收任务能有多大的提前量去填缓冲，不决定速率。

**收编的理由与代价**：`managed_components/` 已入库忽略、由依赖锁重建，**写在那里的任何改动都会在下次依赖解析时消失**，故不能就地改。收编后上游更新不再自动流入，这是本决策的主要代价，须在组件目录留下「本仓改了哪几处」的说明。

### 3. 基线层（自测入口 + 配置契约）

- **设备端吞吐自测入口**（作为一个 `self.` 设备工具）：报告均值 / 中位数 / 最小值 / 字节数 / 耗时 / 信号强度 / 信道 / 当前省电档。选它而非「读 OTA 每秒日志」，因为后者只有升级时才有数字且抖动跨 3 倍（见证据表）。
- **配置契约断言**（纯逻辑，随提交运行）：解析 `sdkconfig.defaults` 与 `sdkconfig.defaults.esp32s3`，断言吞吐相关选项不低于目标值。**这条不可省**——配置被改回低值后设备仍能正常启动，运行时行为覆盖不到这种回退。
- **验收阈值**：自测均值 ≥ **200KB/s**、最小值 ≥ **100KB/s**；内容/音乐路径 ≥ **32KB/s**（4× 于 64kbps 消耗）。名义目标，实施时按实测校准。
- **不倒退约束**：待机省电档不变、对话期全速档不变（ADR-0003）、内部 RAM 运行余量不跌破历史断连水位（free sram 曾跌破 17KB 导致 WiFi 断连）。
- **一次只改一组**：配置层与组件层分两次 OTA 各测一次。ADR-0008/0009 的共同教训是「多项混改会丧失归因能力，逐项排除走了 6 版」。

## Consequences

- **屏幕上的瞬时速度不再被当作链路指标**：OTA 进度显示改为「滑动中位数 + 累计平均」，瞬时值只进串口（串口是取证源，屏幕是体验面）。这条纪律比数字本身更重要——本次误判正是从误信屏幕数字开始的。
- **两处上限的修改点在本仓之外**：不改上游组件，配置层做得再对也够不到 200KB/s，因为搬运任务优先级为 1、接收缓冲 1500 字节、反压 8KB 三处写死在组件里。这是「配置改不动吞吐」这个直觉的例外，须在实施时先做配置层再收编组件，否则无法归因。
- **收编产生长期维护成本**：组件更新需手工比对，且与 ADR-0002 已登记的同类问题（`78__esp-wifi-connect`、`txp666__otto-emoji-gif-component` 也是不入库的本地修改组件）叠加——本项目已有 **3 个**本地修改的组件靠「构建前复制」或「收编」维持，这条路径上没有上游自动同步。下次再有第四个时，应当先问是否该整体转 fork 工作流。
- **内存余量成为回归观测项**：恢复 IRAM 加速吃 27KB 剩余堆，放大接收缓冲再吃内部 RAM。改动后须复核段占用与运行余量；余量跌破安全间隔时，优先回收的是缓冲放大项（它是收益递减的一端），不是 IRAM 加速（它是吞吐的主要来源）。
- **待机功耗不受影响**：本决策只动驱动/协议栈参数，不动省电档的设定点与让位机制（ADR-0009 的范围）。
- **不是 bug 的假问题，勿修**：`CONFIG_ESPTOOLPY_FLASHMODE` 的字符串值是 `dio` 而 QIO 选项开启，这是 IDF 的正常设计（bootloader 先以 DIO 烧写、启动后自行升级到 Quad 模式）。
- **若仍不达标，排查方向在设备之外**：2.4GHz 信道拥塞与同频干扰、AP 的省电/聚合设置、距离遮挡、其它高流量设备。这些属另一张票，本 ADR 不为它们留口子。

## 实施进度

- **2026-09-12：配置层（第 1 项）已落地，等待设备实测验收。** 固件 2.4.24 构建通过，产物 3,491,328 字节。契约测试 `firmware/scripts/tests/test_network_throughput_defaults.py` 已随配置一起入库（5 个用例，纯逻辑、不碰设备）。组件层（第 2 项）与基线层（第 3 项）未动。
- **配置层改动的取证口径**：`sdkconfig` 由 `scripts/build.py zhengchen/minicam --name zhengchen-minicam` 重新生成（**不可裸跑 `idf.py reconfigure`**——那会丢掉板卡身份与寻址，已实测会把 `CONFIG_OTA_URL` 掉回官方云地址）。重新生成后的语义 diff 只有两组：本次吞吐项，以及一组**预存漂移**——`CONFIG_EMOTE_DEF_BG_COLOR/FONT_COLOR` 入库值是黑底白字（`0x000000/0xFFFFFF`），重新生成后回到板卡预设的米色底黑字（`0xC2B280/0x000000`），与 `main/boards/zhengchen/minicam/config.json` 一致。该漂移先于本 ADR 存在，本次顺带修正，需在设备上确认屏幕配色符合预期。
- **待办**：配置层上机测吞吐；通过后再做组件层（收编上游网络组件），两层不得混在一次 OTA 里。

## 附：术语

新增**网络吞吐基线**：设备端吞吐自测入口 + 入库的目标数值契约 + 本条 ADR 的验收阈值三者合称；与**管线遥测**（音乐播放链路的 `pipe:` 行）是两套指标，前者测链路、后者测播放链路，勿混。
