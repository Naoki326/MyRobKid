# 独占资源的让位机制：暂不抽通用仲裁，音乐先做可恢复占用者的样本

设备的五个资源（扬声器、麦克风/唤醒词、WiFi 省电等级、屏幕、PSRAM/CPU）目前全靠手工调用协调，调用点随占用者数量平方增长，已经出现不对称漏判。**扬声器尤其不是锁，而是一条谁都能追加的 FIFO 队列 + 各自手动 flush 的约定**。决定**暂不抽通用资源仲裁者**，而是让「音乐暂停/续播」先按「占用者登记（优先级 + 让位方式）」的形状落地，作为可恢复占用者的第一个样本。

注意区分四层，它们的验证程度不同：

| 层 | 样本 | 状态 |
|---|---|---|
| 内容形态（有限/直播） | 歌曲、播客、B站、电台 | **4 个，已验证**（电台是有限/直播的反例）|
| 抢占策略 `Reject` / `Stop` / `Mix` | 通知 / TTS / 音效 | **3 个，已验证** |
| 抢占策略 `PauseResumable` | 无 | **0 个** —— 音乐是正在设计的第一个 |
| 可恢复的**恢复语义** | 无 | **0 个** —— 音乐是第一次尝试，且尚未实现 |
| 嵌套归还 | 无 | **0 个 —— 这才是暂不抽象的真实理由** |

即：不是「样本不足」，而是缺样本的恰好是恢复语义与嵌套归还这两层；前两层可直接定。

**关键：样本要按轴数，不是按内容数。** `MusicPlayer::Start(std::string url, FinishedCallback)` 只有一个参数，无内容类型——四类内容共用同一台播放器、同一套解码、同一条 TCP 反压。所以它们不是「暂停的第 2/3/4 个样本」，而是**同一个样本重复了四次**：暂停是播放器级能力，天然通用。真正按内容分岔的是**续播**（见下）。

## 什么是「恢复语义」

`PauseResumable` 这个名字承诺了一对动作。前半句（被抢占时不死，冻结在位点）接口说得清；**后半句是恢复语义**，它要回答四个接口目前答不了的问题：

1. **谁按播放键**——直觉是「谁抢走谁还回来」，但音乐的实际答案**不是释放者**：TTS 说完（释放）与音乐恢复之间隔着 6–8 秒静默等待，因为用户在这段时间里还在聆听、可能追问。恢复由**计时器**驱动，而释放链只标记「该恢复谁」。
2. **恢复到哪**——位点须减掉 ring 预缓冲，再回退 1–2s 安全余量（宁可重复不跳词）。
3. **失败怎么办**——不是原子操作而是降级阶梯：复用原连接 → 试读 2–3s 无数据判死 → 按位点重取 → 仍失败则音效提示 + 回 Listening。
4. **何时不该恢复**——用户暂停（需说「继续」）/ 用户停止 / 换歌 / 会话结束，需要一组抑制条件；缺任一条就会出现「用户说暂停，聊一句音乐自己回来了」。

嵌套归还则是恢复语义里最难的一格：A 被 B 抢占、B 又被 C 抢占，C 释放时该恢复 B 还是 A？若两者都可恢复则这是一个栈，而栈的深度、同层冲突、A 在 B 仍持有期间被再次抢占，均无先例。

## Context（取证链）

2026-09-11 设计音乐暂停/续播时，为确定改动波及面而清点，发现五处资源都是散的：

| 资源 | 协调手段 | 调用点 |
|---|---|---|
| 扬声器 | 手工 `audio_service_.ResetDecoder()` | `application.cc` 6 处 |
| 麦克风/唤醒词 | 手工 `EnableWakeWordDetection()` | 11 处（另 2 处在 `sleep_timer.cc` / `power_save_timer.cc`）|
| WiFi 省电等级 | last-writer-wins，无引用计数 | 16 处 |
| 屏幕 | last-writer-wins | 分散 |
| PSRAM/CPU | 手工调参 | 见 ADR-0008 |

`ResetDecoder()` 的语义是「把解码队列与播放队列全清 + 换代」（`audio_service.cc:813`）。每个新的扬声器占用者都必须记得自己手动调一次，忘一次就串音。

**已存在的不对称漏判**（本 ADR 不修，仅登记）：

- `StartMusic`（`application.cc:1190`）拒绝在通知期间起播；
- `StartNotification`（`:1143`）只查 `notify_player_.IsBusy()`，**从不查 `music_player_.IsBusy()`**；
- 而音乐正是在 `kDeviceStateIdle` 下播放的，故状态判断放行 → 通知可以叠在正在播放的音乐上，`ResetDecoder()` 清掉音乐的 PCM，而音乐 worker 继续推帧，两条流喂同一个 opus 解码器。

判断「音乐在播」与「音乐在对话」现在还混在 `IsBusy()` 与两处 `StopMusic()`（`:826`、`:895`）里，语义要分家：唤醒/新对话 = 让位（暂停），`stop_music` 工具 = 真停止。

## Considered Options

**为什么不并入 `DeviceStateMachine`**：它管的是对话生命周期（one-of-N、白名单转移），而资源占用是**正交的多维**——扬声器归属、麦克风模式、屏幕内容可以独立组合，单个 enum 表达不了。代码已经证明了这个错配：音乐被迫在 `kDeviceStateIdle` 下播放（枚举里没有它的位置），而通知却拿到了专属状态 `kDeviceStateNotifying`。同一个事实「我不空闲」走了两条相反的路。将来若抽仲裁者，它应当是 `DeviceStateMachine` 的**邻接**结构，而不是它的一个分支。

**扬声器的真实形状不是锁**：四个占用者都往同一条 `audio_playback_queue_` 追加（TTS `application.cc:1368`、通知 `notify_player.cc:220`、音乐 `music_player.cc:367`、音效 `audio_service.cc:784`），清场靠各自手动调 `ResetDecoder()`（6 处）。没有一处决定「谁在持有扬声器」，只有一堆各自为政的约定。音效最典型：它不清场直接插入队列，于是与音乐 PCM **拼接**而非混音——没人设计过，是队列的副作用。因此将来若抽仲裁者，**不能假设扬声器是单一独占锁**，必须容纳「叠加/插入」这类非独占占用。

**四种资源有四种不同的组合代数，不能统一**：清点后发现把它们塞进一个统一的 `Acquire/Release` 仲裁器是错的：

| 资源 | 组合代数 | 现状（症状即证据） |
|---|---|---|
| 扬声器 | 优先级 + 抢占策略 | 手工 if 链 |
| 麦克风 | OR / 引用计数 | 手工「我记得恢复」（`application.cc:990` 注释）|
| 省电等级 | max / fold | 手工 fold：`if (!music_player_.IsBusy())`（`:590`、`:1284` 两处重写同一逻辑）|
| 屏幕 | last-writer-wins | 无仲裁 |

麦克风与省电**根本不需要抢占语义**，一个引用计数就够，比扬声器简单一个数量级；而这两处的散落调用最多（11 处 / 16 处），最值得先修。**这是「暂不统一」比「样本不足」更硬的理由。**

**为什么现在不建框架**：

1. **真正缺样本的是「恢复由谁驱动」。** 内容形态与抢占策略都已有 4 个样本，可直接定；但「嵌套归还」一个样本都没有：音乐会话性暂停期间通知拿走扬声器，通知结束后**不应**立即归还音乐——音乐何时恢复由对话结束后的静默计时器决定，而非由归还事件决定。恢复的驱动源是计时器而不是释放链，这一点没有先例可循，现在拍接口就是猜。
2. **与功能改动混做会丧失归因能力。** ADR-0008 的记录是「逐项排除走了 6 版，遥测一加 2 版收敛」。资源重构碰的是同一批文件与同一批失败模式（AFE、TCP 吞吐、PSRAM）。若与音乐暂停同时进行，出现卡顿无法判断是哪一边引起的。
3. **记录「刻意不抽象」本身就是价值。** 后来者看到 6 处 `ResetDecoder()` 会想动手统一；本 ADR 说明为何不能一刀切。

## 已定的接口（扬声器）

以下形状仅用于扬声器。内容形态与抢占策略各由现成样本支撑；标「留白」的那一格接口不表态。

```cpp
// 内容形态 — 样本：歌曲/播客/B站(Finite) vs 电台(Live)
enum class ContentKind { Finite, Live };

// 抢占策略 — 四个占用者各一个样本
enum class Preempt {
    Reject,          // 样本：通知被忙设备拒绝        (application.cc:1143)
    Stop,            // 样本：起播前 ResetDecoder 弃之 (:1215)
    PauseResumable,  // 样本：无 ← 音乐是第一个
    Mix,             // 样本：音效不清场直接插入       (audio_service.cc:784)
};

struct SpeakerClaim {
    const char* name;      // "music" / "notify" / "tts" / "sfx"
    int priority;          // 现有 if 链已隐含：sfx > notify > music
    Preempt when_preempted;
};

enum class AcquireResult { Granted, GrantedPreempted, Rejected };

void Release(const char* name);
// 留白：只标记「该恢复谁」，不直接恢复。
// 嵌套时由谁驱动恢复（计时器 vs 归还链）没有样本，接口不表态。
```

## Consequences

- 音乐暂停/续播须实现为「登记为可恢复占用者」的形状：占用者声明优先级与让位方式（拒绝 / 停止 / 可暂停可恢复），即使眼下登记表只有一个硬编码条目——**接口先对，实体后补**。「答完自动续播」由此得到：让位方归还资源时**标记**待恢复，实际恢复由静默计时器触发（而非归还事件直接恢复，见上）。
- **内容形态（有限/直播）必须由音乐会话记录**：四类内容同走一个播放器（`Start(url)` 签名可证），暂停天然通用；但**续播按内容分岔**：歌曲/B站定位到原处，播客同理但价值最大（30–90 分钟），**直播电台不是「跳到 45:00」而是「回到现在」——位点必须丢弃，而非拒绝**。若把「已播时长」当作可定位偏移去重取直播流，就会给 ffmpeg 一个无意义的输入定位。设备当前无法区分这四类，因为 URL 里只有 `src`/`referer`，没有内容形态与时长。
- **播客是续播价值最大却最拿不到元数据的一类**：`_latest_episode` 只返回 title / url / pub_date，同时长也从 RSS 未解析；歌曲的 `interval` 与 B站的 `duration_s` 也仅用于列表显示，未下发设备。元数据随 `play_url` 下发因此是**续播正确性的前提**，不只是“屏幕显示歌名”的铺垫。
- 抢占策略枚举已被现有四个占用者验证，可直接定；**勿把扬声器假设为单一独占锁**，接口需容纳叠加/插入式占用。
- **通知是下一个迁移对象**，它迁移过来时是本决策的复核点：届时若「嵌套归还」有了第二个样本，再决定是否抽通用仲裁者。
- **麦克风与省电是两个独立的、更简单的收敛目标**：二者都是引用计数（OR / fold），不含抢占语义，且散落调用最多（11 处 / 16 处）。引入 `require`/`release` 后 `if (!music_player_.IsBusy())` 这类手工 fold 与「我记得恢复」注释即可消失。可单独排期，不必等扬声器仲裁，也不必等音乐。
- 上述不对称漏判是真实缺陷；本 ADR 只登记不作为，修复与否另行决定。
